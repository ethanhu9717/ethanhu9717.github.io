# Beacon 设计方案报告

> **文档版本：** v0.1 · 建议基线  
> **编制日期：** 2026-09-20  
> **项目阶段：** 产品定义与 MVP 设计  
> **适用范围：** 自用、单作者、单站点的写作与发布系统  
> **核心框架：** 产品定位 → 产品体验 → 品牌识别  
> **建议品牌表达：** Beacon — Broadcast your ideas. / 让思想发出自己的信号。

---

## 0. 执行摘要

Beacon 建议定位为：**一个为个人作者提供专注写作、内容管理与可靠发布的轻量系统，通过 GitHub Pages 向读者呈现独立网站。**

它不是为了重做一个功能齐全的通用 CMS，也不是因为采用 vibe coding 开发，就必须加入 AI 聊天、自动生成或自主发布。第一版的价值，应集中在一件事上：**让作者从开始写作到确认文章上线，始终清楚内容在哪里、保存到哪一步、发布的是哪个版本。**

本方案建议采用“本地创作、显式发布、静态展示”的工作模式：本地运行写作后台和发布服务，文章以可迁移的 Markdown 文件保存；作者主动发布时，系统生成明确的发布快照，推送到独立站点仓库，由 GitHub Actions 构建并部署 GitHub Pages。GitHub Pages 是静态站点托管服务，不承担 Beacon 的 Python 后端、数据库写入或后台鉴权服务。[^s1][^s2]

三个层次对应三项承诺：

| 层次 | Beacon 的设计重点 | 成功的具体表现 |
|---|---|---|
| 产品定位 | 个人写作与可靠发布，边界清楚 | 新功能不会偏离写作—发布主流程 |
| 产品体验 | 不丢稿、不误发、可验证、可恢复 | 能完整完成写作、预览、发布、更新、撤下 |
| 品牌识别 | 安静、清晰、独立、持续发声 | 名称、符号、文案和界面保持一致 |

**建议优先级：内容安全与发布正确性 → 写作流畅度 → 阅读质量 → 品牌精细度 → 扩展功能。** 这不是忽视品牌，而是避免让一个漂亮后台掩盖不可靠的保存和发布机制。

## 1. 对前述讨论的分析与修正

### 1.1 保留的主线：定位是承诺，体验是兑现，品牌是表达

这套三层结构适合 Beacon 的早期设计，但不是所有产品问题的完整分类。技术实现、成本、安全和维护是支撑三个层次的约束，不必为了完整而机械增加一层“技术品牌”。如果未来从自用转向商业化，还需要另行评估需求验证、获客、收费和持续服务责任；现在不提前建设。

三层之间也有交叉。字体影响品牌识别，也影响阅读；内容可迁移是定位原则，也必须由文件格式和导出功能兑现。因此应以“决策影响什么”划分，而不是强行让每个要素只能属于一层。

### 1.2 名称与寓意不应扩大第一版需求

Beacon 的信标意象可以承载长期表达与传播，但不意味着第一版必须具备跨平台分发、邮件订阅系统、实时广播或复杂渠道管理。当前“推送”的默认范围，是将作者确认的文章版本发布到 GitHub Pages，不自动扩展为公众号、X、视频号等平台联动。

同样，“个人发布系统”是有用的产品定位，不应被解释成必须比博客或 CMS 更大。技术上，Beacon 可以就是一个以写作和发布为核心的轻量个人 CMS。

### 1.3 Slogan、功能说明和操作按钮分开设计

建议只保留一条主 Slogan：**Broadcast your ideas.** 中文品牌表达为：**让思想发出自己的信号。** 两句表达对应同一概念，不要求逐字互译。

“Write. Publish.” 更适合做功能副标题；“Personal Publishing System” 是产品类别。三者承担不同职责，不在一个界面反复堆叠。

此前建议用 Broadcast 替代 Publish 作为操作按钮，本方案作修正：**品牌可以有隐喻，关键操作应优先明确。** 第一版使用“发布”“更新发布”“撤下”，不要求用户先理解广播隐喻。

### 1.4 本地优先和内容自主必须有具体边界

本地优先在本方案中意味着：互联网断开时，只要本地服务仍运行，作者仍能写作、保存和预览；联网操作集中在推送、部署和状态确认。它不意味着浏览器关闭、后台退出后仍能自动保存，也不意味着自带多设备同步。

内容自主在本方案中意味着：正文、附件和必要元数据可以完整导出，不依赖 Beacon 才能阅读和继续编辑。Git 提交记录不应被当作独立备份、版权证明或作者身份的法律保证。

### 1.5 参考图应提炼设计原则，而不是复制“人格”

用户提供的图中可见不同的表达路径：字母标识、动物符号、放射图形、几何结状图案以及黑白高对比图标。可以据此观察轮廓、留白、配色和独立符号的作用，但不能仅凭图标就判断产品真实人格或成功原因。

Beacon 应借鉴的是：**一个明确概念、一种稳定轮廓、一套可复用视觉规则。** 不模仿某个现有产品的具体图案，也不为“像 AI 产品”而使用相似的放射花形或几何结。

## 2. 第一层：产品定位

### 2.1 产品定义

**中文定位：** 面向个人作者的写作与发布系统，让文章从本地草稿可靠地成为公开网页。

**英文定位：** A personal writing and publishing system for the open web.

这里的核心不是“管理很多内容类型”，而是降低日常写作、技术发布和长期维护之间的切换成本。第一版优先支持文章；不要把知识库、社交平台、素材库和自动化研究 Agent 一并塞进 Beacon。

### 2.2 两类使用者与两种任务

| 使用者 | 主要任务 | 设计关注 |
|---|---|---|
| 作者：Dan | 写作、保存、整理、发布、修正和维护内容 | 专注、反馈明确、可恢复 |
| 读者 | 发现文章、顺畅阅读、引用链接、订阅更新 | 文字清晰、链接稳定、加载合理 |

单作者不等于只设计作者体验。后台好用而网站难读，仍然没有完成产品目标。

建议用以下任务陈述约束需求：

> 当我产生一个值得写下的想法时，我希望立即开始写作，不先处理网站配置；当文章准备好时，我希望把自己确认的版本发布到网站，并知道读者看到的确实是这个版本。

### 2.3 核心价值主张

**写作不中断。** 初次配置完成后，写作、保存和预览不依赖远程平台即时响应；管理操作不抢占正文空间。

**发布有证据。** 系统不仅告诉作者“命令执行完了”，还要记录版本、远程提交、部署结果和线上验证状态。

**内容能带走。** 正文使用开放文本格式，图片和元数据一起导出；站点生成器或托管平台替换时，不必先救出内容。

### 2.4 产品原则与对应取舍

| 原则 | 必须兑现的行为 | 因此暂不做什么 |
|---|---|---|
| Writing first | 默认进入继续写作或文章列表 | 复杂运营仪表盘 |
| Explicit publishing | 保存不会自动公开；发布前显示影响范围 | 默认自动发布 |
| Portable content | Markdown、附件与元数据可导出 | 仅保存编辑器私有 JSON |
| Observable workflow | 分清保存、推送、部署、线上确认 | 只有一个“成功”提示 |
| Small by default | 单作者、单站点、单渠道 | 多租户、插件市场、复杂权限 |

### 2.5 与 Orbit 的职责边界

建议保持：**Orbit 管素材，Beacon 管文章与发布。**

Orbit 可负责素材原件、来源、版本和可用性记录；Beacon 负责文章正文、网站用图、图注与发布版本。两者可以共享视觉规则，但不共享业务数据库，也不让 Beacon 直接修改 Orbit 表结构。

第一版采用低耦合方式：从 Orbit 导出已选图片及相关说明，再导入 Beacon。未来如果确有需要，增加只读查询或导出接口。**停止 Orbit 后，Beacon 已发布的网站仍应正常展示图片。**

## 3. 第二层：产品体验

### 3.1 总体结构：一个产品，三个内部模块

| 模块 | 职责 | 是否对读者公开 |
|---|---|---|
| Studio：写作后台 | 编辑、预览、文章管理、发布入口 | 否 |
| Engine：本地服务 | 文件保存、版本快照、发布任务、状态核验 | 否 |
| Site：读者网站 | 首页、文章、关于、订阅与索引输出 | 是 |

这些是工程和信息架构名称，不需要包装成三个独立子品牌。用户只需理解：Beacon 是工具，公开博客是作者自己的站点。

### 3.2 作者后台的信息架构

主导航建议控制在四项：“写作”“文章”“发布记录”“设置”。

“写作”优先恢复最近编辑的文章，没有文章时进入空白编辑器。“文章”采用同一文章集合中的筛选，不创建互不相通的草稿库和已发布库。“发布记录”用于排查问题与恢复版本；“设置”容纳站点信息、GitHub 连接、工作区、备份和外观。

不在第一版增加独立媒体资产管理页面。图片作为文章附件管理，避免重做 Orbit。

### 3.3 首次使用与空状态

首次启动分两步，而不是强制先完成全部 GitHub 配置。

**先建立写作空间。** 选择工作区，创建文章，确认本地保存和预览可用。

**再连接发布目标。** 填写或选择站点仓库、发布分支、站点地址，检查凭据与 Pages 配置，使用不含敏感信息的样例完成一次部署。

GitHub 未连接时显示：“可以继续本地写作；连接 GitHub 后即可发布。”不要让网络或授权问题阻止作者进入编辑器。

### 3.4 编辑器设计

正文采用 Markdown，辅助提供常见格式按钮、图片插入和预览。建议使用成熟的编辑组件，不在第一版自研富文本内核。

页面中心是标题与正文；顶部只保留返回、保存状态、预览和发布。摘要、标签、固定链接等元数据放在可收起侧栏。标题可以修改，文章 ID 不变；公开链接按后文的 slug 规则管理。

第一版编辑能力限定为段落、标题、列表、引用、链接、图片、代码块和表格。脚注、数学公式、复杂嵌入、双链、块级引用和 MDX 暂不承诺；选定 Markdown 方言后，本地预览和生产构建必须使用一致的规则。

中文输入法需要专门测试：候选词确认期间不能因自动格式化、保存或快捷键劫持造成重复字符、光标跳动或文本丢失。

### 3.5 保存与恢复

自动保存的设计目标是：正常负载下，停止输入后约 2 秒内完成本地持久化确认。这个数字是待验证目标，不是已测性能。

界面至少区分“正在保存”“已保存到本地”“保存失败”。只有后端确认文件写入成功后，才能显示已保存；前端发出请求或修改内存状态，都不算保存完成。

写入采用同目录临时文件、校验和替换的方式，避免直接覆盖导致文件截断。保存请求带当前版本摘要，检测到其他标签页或外部编辑器已修改文件时拒绝静默覆盖，提示比较版本。

浏览器崩溃恢复缓冲可以作为补充，但不能成为正文的唯一存储。必须明确：**已确认保存的内容，应通过进程中断与重启测试；尚未确认保存的内容不能被承诺绝不丢失。** 本地服务停止时立即显示异常，而不是假装离线保存成功。

### 3.6 预览与发布前检查

编辑器即时预览用于检查结构；正式发布预览应复用 Site 的文章模板与构建配置。采用同一渲染规则并测试样例，可以降低预览与线上显示不一致的风险，但仍需验证资源路径与托管环境。

发布前显示本次操作的文章、标题、公开链接、摘要、图片和变更范围。缺失图片、非法路径、重复 slug、无效元数据必须阻断发布；缺少摘要或可选标签可以提示后继续。

图片需有适当的替代文本，装饰性图片可以显式设置为空。图注、来源和授权记录由作者维护；系统不得因为“有图源链接”就自动标记“可合法发布”。

### 3.7 三条状态线，不能混为一个字段

**保存状态**描述当前文本是否已落盘；**内容发布状态**描述本地版本和线上版本的关系；**发布任务状态**描述某次部署执行到了哪一步。

| 内容发布状态 | 建议判定方式 |
|---|---|
| 草稿 | 没有当前线上版本 |
| 已发布 | 本地可发布内容摘要与最后已确认线上版本一致 |
| 有未发布修改 | 存在线上版本，但本地内容与其不同 |
| 已撤下 | 过去发布过，最近已确认的站点版本不再包含它 |

本地归档或回收站是另一种管理状态，不应自动表示文章已从网站撤下。

发布任务建议包含：`queued → validating → snapshotting → pushing → building → deploying → verifying → succeeded`。异常分为 `failed`、`unknown` 或其他明确的终止状态；无法读取远程状态时显示“待确认”，而不是把超时直接等同于部署失败。

例如：“本文已保存到本地；线上仍是上一版本；本次发布卡在构建阶段。”这比笼统的“发布失败”更有行动价值。

### 3.8 发布快照：避免误发其他文章的新修改

Pages 发布对象是整个站点，因此“发布一篇文章”不能简单地把整个工作区最新内容全部推上去。

例子：A 文章已有线上版 v1，本地正在修改 v2；B 文章准备发布。点击发布 B 时，站点应包含 **A 的已发布 v1 + B 的确认版本**，而不是顺带公开 A 的 v2。

本方案因此要求每次构建读取一个明确的发布清单：以当前线上站点版本为基础，只替换作者本次选择的文章、页面或设置；其他条目继续使用原已发布快照。预览和实际发布应使用同一份候选快照。

### 3.9 可靠发布流程

作者确认发布后，Engine 应依次执行：保存并校验所选内容；创建不可变站点快照和唯一 `release_id`；记录本地任务；将允许公开的文件放入受控站点工作目录；检查远程变化；提交并推送；找到与该提交对应的构建和部署任务；确认线上返回匹配的版本标记。

GitHub 官方支持使用 Actions 构建静态文件、上传 Pages artifact 并部署。本方案选择这条流程，而不是自行维护上传服务器。[^s2]

重试必须复用同一发布意图和内容快照，不能顺手包含重试期间的新修改。为防止网络超时导致重复提交，重试前先检查远程是否已经存在该次发布。第一版每个站点串行发布，避免旧任务在新任务之后覆盖网站。

**推送成功不等于上线成功。** 只有部署证据和线上标记匹配后，后台才显示“已确认上线”。验证失败时可显示“部署已完成，线上版本待确认”；后续重新检查，不要求重新生成内容。

### 3.10 更新、撤下与恢复

“更新发布”仅更新已选文章；未发布的本地修改保持私有。“撤下”是生成不包含该文章的新站点版本，且同步更新首页、RSS、站点地图及相关索引。只有新版本已确认上线，才显示已撤下。

已发布文章移入回收站前，要求作者明确选择撤下或仅本地归档；第一版可采用更简单规则：必须先撤下，才允许进入回收站。删除本地文件不能被误认为线上页面已经消失。

恢复旧站点版本应通过一次新的发布记录完成，保留操作证据，不默认执行强制推送和改写历史。站点撤下只代表本站后续不再提供该页面，不承诺删除外部缓存、历史副本或公开仓库既有历史。

### 3.11 读者网站

第一版公开页面建议为：首页、文章页、关于页、404；同时生成 RSS 与 sitemap。归档页、标签页与全文搜索放在后续版本，不因后台有标签字段就必须同时实现所有前台筛选。

首页直接呈现作者身份、简短介绍和文章，不用占满首屏的产品宣传横幅。文章页优先标题、摘要或导语、日期、正文与图注；目录只在确有较多章节时展示。

博客站点名称应独立于 Beacon 产品名称。作者可以使用自己的姓名或另定站名；Beacon 只需在页脚低调标注，不要求读者先理解软件品牌。

阅读样式建议以中文长文为基准：正文约 18–20 px、行高约 1.75–1.9、桌面正文宽度约 680–760 px，移动端保留适当边距。这些是初始试排参数，不是通用最佳值，需使用真实长文调整。代码与宽表格允许局部横向滚动，但整页不应溢出屏幕。

## 4. 第三层：品牌识别

### 4.1 品牌核心

**Beacon：安静地写作，清晰地发声。**

“灯塔指引”保留为稳定、可被发现的意象，而不是把个人博客包装成替他人决定方向的权威。更适合本项目的解释是：把经过思考的内容持续发布，让它在需要的时候被人找到。

建议人格为：**安静、专注、独立、清晰。** 将这些词转换为行为：安静意味着没有无关提醒；专注意味着写作优先；独立意味着内容可迁移；清晰意味着操作和状态不故弄玄虚。

### 4.2 品牌表达体系

| 项目 | 建议内容 | 使用位置 |
|---|---|---|
| 产品名称 | Beacon | 应用、仓库说明、关于页 |
| 产品类别 | Personal Publishing System | README 与产品介绍 |
| 主 Slogan | Broadcast your ideas. | 品牌介绍、启动页 |
| 中文表达 | 让思想发出自己的信号。 | 中文介绍与传播文案 |
| 功能副标题 | Write. Publish. | 简短功能描述，可选 |
| 核心操作 | 发布 / Publish | 编辑器按钮 |
| 产品定位句 | 一个专注写作与可靠发布的个人内容系统。 | 给首次接触者解释用途 |

主 Slogan 仍是建议，尚未经过用户最终确认。产品首次使用时需要明确功能描述，不靠一句口号承担所有解释工作。

### 4.3 Logo 设计方向

建议优先探索“抽象信标”：一个稳定的中心或主体，配合一至两道向外延伸的光束，通过负空间体现传播。尽量使用少量几何形体，而不是画完整海岸、灯塔建筑、星空和火箭。

与图中现有产品建立区分：不做多瓣放射花形，不做复杂交织几何结，也不直接复制类似的圆形斜切结构。B 字母可以作为次选方向，但不能为了塞入字母牺牲轮廓清晰度。

验收应覆盖纯黑、纯白、浅底、深底以及 16 / 32 / 64 / 128 px 预览。小尺寸不得出现关键结构糊成一团或线条消失的问题。圆角方形作为应用图标容器，符号本身应可脱离容器使用。

这些是设计任务与测试要求，不代表本报告已经生成或批准了 Logo。

### 4.4 色彩与字体方向

建议采用“纸张 + 墨色 + 一束暖光”的视觉概念。首版以中性色为主体，琥珀色少量用于主要动作和品牌强调。以下是待验证的起始色值，不是已通过所有对比度组合测试的完整设计系统。

| Token | 建议值 | 用途 |
|---|---|---|
| `background` | `#F7F5F0` | 浅色阅读背景 |
| `surface` | `#FFFFFF` | 编辑区域与面板 |
| `text-primary` | `#1C1C1C` | 正文 |
| `text-secondary` | `#62615D` | 次级说明 |
| `border` | `#DEDAD2` | 轻分隔 |
| `accent` | `#A56417` | 浅色主题强调色 |
| `dark-background` | `#111315` | 后续深色主题背景 |
| `dark-text` | `#ECEBE7` | 后续深色主题文字 |
| `dark-accent` | `#E7AE58` | 后续深色主题强调色 |

后台优先系统无衬线字体，减少初期字体分发和渲染差异；正文先用成熟的中文系统字体栈，代码使用系统等宽字体。暂不引入多套在线字体和复杂字体加载流程。

可读性按实际前景—背景组合验收。WCAG 的最低对比度标准中，普通文字通常要求至少 4.5:1，大号文字至少 3:1；品牌配色不能替代具体检查。[^s6] 同时要求键盘焦点可见、交互有文字含义、错误不只靠红色传达。

第一版不必同时完成多主题。先完成一个阅读和编辑都稳定的主题，再添加深色模式；提前用 Token 管理颜色即可。

### 4.5 界面文案与动效

文案应说明实际发生的事情，尽量使用短句，但不省略关键条件。

| 场景 | 建议文案 | 避免 |
|---|---|---|
| 保存成功 | 已保存到本地 | 已同步一切 |
| 推送成功 | 已推送，正在构建网站 | 发布成功 |
| 部署后未核验 | 部署已完成，线上版本待确认 | 立即认定成功或失败 |
| 发布成功 | 已确认上线 · 查看文章 | 你的思想已征服世界 |
| 构建失败 | 构建失败，线上仍为上一版本 | Error |
| 空状态 | 写下第一篇文章。 | 冗长的品牌宣言 |

交互动效服务于状态变化，不做持续扫描、闪烁灯塔或背景星空。尊重减少动态效果的系统设置。发光效果可在品牌展示中探索，但不作为阅读界面的常态。

### 4.6 Orbit 与 Beacon 的家族关系

统一之处建议为：排版原则、间距体系、图标笔画、圆角尺度、克制的文案。差异建议为：Orbit 表达收集、关联与沉淀；Beacon 表达写作、发布与发声。

不要求两个产品共用 Logo，也不在本次方案中未经确认改造 Orbit 的现有视觉。两者首先是独立好用的工具，然后才是一套协调的个人软件体系。

## 5. 技术架构与部署方案

### 5.1 基础约束

GitHub Pages 提供静态站点托管，可展示构建后的 HTML、CSS、JavaScript；本方案因此把后台与数据库留在本地，把公开展示交给 Pages。不能将 FastAPI 或需要运行时服务器的功能直接放到 Pages 上运行。[^s1]

私有源仓库不等于网站内容私有。GitHub 官方明确提醒 Pages 网站可能公开，即使源仓库是私有的；是否支持从私有仓库使用 Pages，还取决于账号计划或组织条件。首次部署必须核实账户与设置，不预设免费私有发布可用。[^s3]

### 5.2 推荐架构

```text
作者浏览器
    │ 本地同源访问
    ▼
Beacon Studio ──► Beacon Engine
                      │
                      ├─ Markdown 工作区与附件
                      ├─ SQLite 索引、任务与状态记录
                      ├─ 本地站点预览
                      └─ 发布快照与 Git 发布器
                                  │ 明确确认的公开内容
                                  ▼
                            站点 GitHub 仓库
                                  │
                            GitHub Actions
                                  │ 构建、校验、部署
                                  ▼
                             GitHub Pages
                                  │
                                  ▼
                                 读者
```

该结构不要求公网部署后台，也不要求读者访问时连接作者电脑。发布完成后，公开站点不依赖 Beacon 或 Orbit 进程持续运行，这是本方案的架构要求。

### 5.3 技术选型建议与取舍

| 部分 | 建议 | 理由与边界 |
|---|---|---|
| 写作后台 | React + TypeScript，独立静态构建 | 聚焦交互；不引入与写作无关的服务端前端能力 |
| 本地 API | FastAPI | 文件操作、发布编排集中在一个本地服务 |
| 正文 | Markdown + YAML front matter | 可直接读取、版本比较和迁移 |
| 本地索引及任务 | SQLite | 第一版不引入独立数据库服务 |
| 公开站点 | Astro 静态构建 | 使用构建期 Markdown 内容与静态模板 |
| 发布 | Git + GitHub Actions + Pages | 使用平台已有部署流程 |
| 图片 | 本地管理网站衍生图，按需复制到发布快照 | 不把 Orbit 原件库直接公开 |

Astro 的内容集合支持本地 Markdown 与结构校验，并有官方 GitHub Pages 部署路径，因此适合作为本方案的优先验证对象。这里只选择构建期静态路径，不启用运行时内容接口。[^s4][^s5]

如果复用现有 Next.js 经验更重要，可以替换 Site 生成器，但必须采用静态导出并检查限制。Next.js 官方说明，依赖运行时服务器的功能不支持静态导出，例如 Server Actions、请求相关处理、默认图片优化等；不能在选型时把这些能力默认带入 Pages。[^s7]

**不建议第一版同时维护两种站点生成器。** 先通过一篇真实复杂文章验证一种方案，然后锁定依赖与构建方式。

### 5.4 仓库与私有工作区分离

建议区分两个仓库职责和一个本地数据工作区：`beacon` 保存应用代码，`beacon-site` 保存站点模板与已确认公开的内容快照，本地工作区保存草稿、私有附件、任务状态和恢复信息。名称为示例，不代表已有仓库。

公开站点仓库绝不接收整个作者工作区。即使模板不渲染 `draft: true`，文件一旦推入公开仓库，仍可能通过仓库内容被看到。因此草稿隔离必须发生在导出与提交之前，不能只依赖页面过滤。

```text
BeaconWorkspace/
├── content/
│   ├── posts/<article-id>.md
│   └── pages/about.md
├── media/
│   ├── originals/              # 导入原件，仅本地
│   └── web/                    # 网站用图
├── config/site.yaml
└── .beacon/
    ├── state.sqlite            # 索引 + 任务 + 状态，不含凭据
    ├── releases/<release-id>/  # 不可变快照与清单
    ├── publisher/              # 受控站点仓库工作副本
    └── recovery/               # 临时恢复数据
```

备份目标应是独立位置；在同一硬盘多建一个 backup 文件夹，只能作为局部恢复便利，不能作为本方案的唯一备份。

### 5.5 平台限制如何影响设计

官方文档当前规定已发布 Pages 站点不超过 1 GB，并有带宽、部署超时等限制。[^s8] 因此 Beacon 不把高清原件和大型视频默认放入站点仓库；发布前显示图片及站点体积，对超大资源进行提示或阻断。

用户站点和项目站点的地址结构不同。Site 必须集中处理 `site_url` 与 `base_path`，不要把所有资源路径硬编码为根目录。Astro 官方的项目站点部署说明也要求正确配置 `base`。[^s1][^s5]

目标读者网络中的加载表现需要实测。本报告未验证真实站点的可达性、移动网络表现或部署耗时，不承诺全球一致访问速度，也不承诺所有使用方式零成本。

## 6. 内容模型与数据边界

### 6.1 单一事实来源不是“所有数据只能放一个地方”

建议按数据类型定义权威来源，而不是让文件、数据库和 Git 三方自由编辑同一份正文。

| 数据类型 | 权威来源 | 其他副本的作用 |
|---|---|---|
| 当前正文及文章元数据 | 工作区 Markdown 文件 | SQLite 只建立索引 |
| 当前站点配置 | 工作区配置文件 | 发布时生成配置快照 |
| 某次发布的内容 | 不可变 release 快照 | 站点仓库作为远程发布材料 |
| 本地任务执行记录 | SQLite 任务记录 | 日志便于排查，不替代任务状态 |
| 远程构建/部署状态 | 对应 GitHub 任务证据 | 本地保存最后观测值 |
| 线上版本 | 站点版本标记 + 最近核验时间 | 后台展示最近确认状态 |

删除 SQLite 后可以重建文章索引，但不能声称所有任务历史都能从当前 Markdown 恢复。备份必须覆盖需要保留的任务记录、配置与发布快照；启动后应与远程证据重新核对未完成任务。

### 6.2 文章字段

第一版建议使用：`id`、`title`、`slug`、`summary`、`tags`、`created_at`、`updated_at`、可选封面及正文。内容发布日期在创建发布快照时确定，并在首次发布后保持；后台另行记录实际部署时间和线上核验时间。不能把编辑器保存时间当成发布时间，也不能把内容元数据中的日期当成上线证据。

`id` 是系统身份，不随标题变化；`slug` 是公开 URL 标识，首次发布后默认锁定。第一版不提供直接改已发布 slug 的功能，以避免还未设计迁移和旧链接处理就破坏地址稳定性。`updated_at` 表示工作稿更新时间；公开页的更新日期来自已发布内容版本，不泄露未公开编辑活动。

示例仅表示工作区内容，不表示文章已发布：

```yaml
---
id: "4d7d3938-f2e5-41df-b3b7-0a5d21afdd95"
title: "为什么我想拥有自己的博客"
slug: "why-own-a-blog"
summary: "关于写作、表达与个人内容空间的思考。"
tags: ["写作", "产品"]
created_at: "2026-09-20T10:00:00+08:00"
updated_at: "2026-09-20T10:00:00+08:00"
---
```

### 6.3 发布记录与版本指纹

Release 至少记录：发布 ID、父发布 ID、所选条目、完整站点条目清单、文章及资源摘要、配置/模板版本、创建时间、公开时间语义、Git commit SHA、workflow run ID、状态、错误阶段和最后核验时间。

Git commit SHA 在生成提交之后产生，不能把“本次提交自己的 SHA”预先写入同一提交再要求它保持不变。推荐使用预先生成的 `release_id` 作为端到端标识，在本地记录中关联后续 commit SHA；CI 也可在构建产物中写入已知提交信息。

公开版本标记只包含非敏感数据，例如 release ID、构建时间和必要的内容摘要，不公开本地路径、草稿清单、完整私有元数据或凭据。

### 6.4 文件与数据库之间的失败处理

文件替换和 SQLite 事务不是同一个原子操作。本方案要求用可恢复的步骤处理：先生成并校验快照临时目录，完整落盘后标记为可用，再把任务与快照引用写入数据库。启动时扫描不完整快照、没有任务引用的完整快照和未结束任务，进行清理或核对。

第一版无需引入分布式事务框架，但不能依赖“几条语句通常会一起成功”的假设。测试应覆盖文件写完后数据库失败、数据库任务已建立后进程退出以及远程提交成功但本地未收到响应等情况。

### 6.5 图片与 Orbit 引用

网站用图导入后生成自己的文件路径与内容摘要。可以附带 `orbit_asset_id`、来源 URL、作者、许可说明和图注，但这些字段不构成网站运行依赖。

发布快照必须包含可供读者访问的实际网站图片，或作者明确选择的外部资源地址；不能引用本地磁盘路径或只对作者电脑开放的 Orbit 地址。优先使用受控网站图片，外部资源依赖需明确显示。

不覆盖原件；压缩、裁切和尺寸调整生成衍生图。默认移除不必要的相机位置等元数据，同时保留作者需要公开的图注与来源记录。

## 7. 安全、可靠性与维护

### 7.1 本地后台的安全边界

默认仅监听回环地址，不对局域网或公网开放。前端与 API 优先同源；校验 Host、Origin 和会话/防伪机制，不把“只在本机使用”当作完全无须防护的理由。OWASP 对跨站请求伪造的防护强调令牌、来源验证等措施；CORS 不能代替完整的请求授权设计。[^s9]

后端只允许在选定工作区内操作文件，拒绝路径穿越和越界符号链接。Git 命令以参数数组调用，不把文章标题、路径或仓库配置拼成可执行 shell 字符串。编辑器内容不能触发任意本地命令。

### 7.2 凭据与 Actions 权限

GitHub 凭据只由本地发布服务使用，优先复用受控凭据存储。不得写入文章、配置导出、公共环境变量或前端构建包；日志中需要脱敏。个人访问令牌按用途和仓库范围授予最小权限。[^s10]

CI 使用工作流自身所需权限；Pages 部署所需的 `pages: write` 与 `id-token: write` 等由工作流声明，不把个人长期令牌当作默认部署密钥。官方自定义工作流说明提供了对应权限与环境要求。[^s2]

### 7.3 内容渲染与公开边界

第一版关闭任意原始 HTML 和可执行 MDX，仅允许已确定的 Markdown 能力；对链接、图片 URL 和渲染结果执行适当校验，防止危险协议和脚本注入。OWASP 的 XSS 防护原则包括按上下文编码与必要的 HTML 净化。[^s11]

公开前做白名单导出，并扫描站点仓库与构建产物。检查对象不仅是文章页，还包括 RSS、sitemap、搜索索引、source map、JSON 数据、附件和错误输出。禁止将整个工作区直接作为 Pages artifact 上传。

### 7.4 备份与恢复

建立独立备份，覆盖正文、图片、站点配置、必要的任务数据与发布快照，凭据另行管理。备份导出不包含个人令牌；SQLite 通过一致性快照或停写窗口备份，不简单复制可能处于写入中的文件。

至少进行一次从备份恢复到新工作区的演练，验证正文、图片、站点配置、索引重建和重新发布能力。备份成功提示不能替代恢复测试。

### 7.5 维护原则

锁定依赖版本，记录升级过程；先对样例站点验证再更新常用环境。保存到磁盘、公开发布、撤下文章属于高风险动作，必须有测试覆盖。

首版不引入微服务、Redis、容器编排和通用插件系统。以一个本地服务、一套明确内容格式和一个站点目标完成闭环。发布日志与错误码做到足够排查即可，不建设企业级监控平台。

## 8. MVP 范围与路线图

### 8.1 v0.1 必须完成的范围

| 能力组 | 第一版范围 | 不扩大到 |
|---|---|---|
| 工作区 | 创建/打开工作区，Markdown 导入导出 | 多设备同步 |
| 写作 | 基础编辑、自动保存、图片、预览 | 块编辑器、复杂 MDX |
| 文章管理 | 列表、标题/状态筛选、元数据 | 知识图谱与复杂数据库视图 |
| 发布 | 单仓库、单站点，显式发布和更新 | 多渠道广播 |
| 状态与恢复 | 发布记录、重试、重启核对、上一成功版本恢复 | 通用任务编排平台 |
| 撤下 | 撤下并更新站点相关输出 | 全网内容删除承诺 |
| 阅读 | 首页、文章、关于、404、RSS、sitemap | 评论、会员与访问分析后台 |
| 安全与数据 | 草稿隔离、凭据保护、完整备份/恢复测试 | 企业权限体系 |
| 品牌 | 名称、单一 Slogan、基础图标、一个稳定主题 | 完整品牌手册与主题市场 |

### 8.2 明确延后的能力

归档与标签独立页面、全文搜索、深色主题、全文差异比较、定时发布、远程后台、AI 润色、自动摘要、Orbit API 联动以及多平台分发，进入后续需求池。

定时发布尤其不能只加一个时间字段：本地电脑关闭后谁执行任务、时区如何处理、任务是否可重复执行、失败如何通知，都需要额外设计。因此第一版不宣传定时能力。

### 8.3 按风险推进的里程碑

| 阶段 | 目标 | 完成条件 |
|---|---|---|
| M0：技术贯通 | 用非敏感样例验证静态模板、资源路径和 Pages 部署 | 一篇复杂样例正确上线，确定技术路径与账号条件 |
| M1：写作工作区 | 实现编辑、文件持久化、图片与本地预览 | 断网可写；保存确认与中断恢复测试通过 |
| M2：可靠发布 | 实现快照、状态、推送、线上核验、更新与撤下 | 误发、冲突、失败、重启和恢复用例通过 |
| M3：v0.1 自用 | 完成阅读样式、基础品牌、导出恢复和全链路测试 | 使用真实文章完成日常发布，不依赖手改产物 |

不在尚未检查代码与环境时承诺具体完工天数。每个里程碑以验收证据结束，而不是以生成了多少文件结束。

## 9. 验收标准与测试矩阵

### 9.1 关键端到端用例

| 编号 | 测试情境 | 通过标准 |
|---|---|---|
| T01 | 互联网断开，本地服务仍运行 | 能新建、编辑、保存与本地预览；明确提示不能发布 |
| T02 | 已显示保存成功后立即退出进程 | 重启后已确认内容完整；不出现截断文件 |
| T03 | 中文输入法、粘贴、撤销重做 | 不重复字符、不丢内容、不异常跳光标 |
| T04 | 两个标签页编辑同一文章 | 发现版本冲突，不静默覆盖 |
| T05 | 首次发布新文章 | 页面、图片与 release 标记匹配；后台显示已确认上线 |
| T06 | 已发布文章继续修改但不发布 | 线上保持原版本，后台显示有未发布修改 |
| T07 | A 有私有新修改，只发布 B | A 线上仍为已发布版；A 新稿不进入仓库或产物 |
| T08 | GitHub 推送/构建/部署各阶段失败 | 显示具体阶段；不错误宣告新版本上线 |
| T09 | 推送响应丢失后重试 | 先核对远程，不重复产生无意义发布，不夹带新修改 |
| T10 | 后台在部署中退出并重启 | 能恢复任务核对；无法确定时显示待确认 |
| T11 | 远程仓库出现未知变更 | 不自动 force push；提示冲突或重新同步 |
| T12 | 撤下文章 | 正文与相关列表、RSS、sitemap 同步更新，已确认后标记撤下 |
| T13 | 恢复上一个成功站点版本 | 形成新发布记录，线上版本与目标快照一致 |
| T14 | 草稿含唯一测试标记与模拟凭据 | 公开仓库和全部构建产物中均不存在标记或凭据 |
| T15 | 项目子路径部署与页面刷新 | 首页、文章、图片、RSS、404 均按正确路径工作 |
| T16 | 从独立备份恢复到新目录 | 正文、图片和配置完整，可重建索引并发布 |
| T17 | 关闭 Beacon 与 Orbit 后访问网站 | 已发布文章及自托管图片仍正常展示 |
| T18 | 360 px 宽屏、桌面、键盘与缩放 | 正文可读，整页无非必要横向溢出，主要操作可用 |
| T19 | 非法路径、危险 URL、未授权本地请求 | 请求被拒绝，不能越界读写或执行脚本 |
| T20 | 文件落盘与数据库写入之间故障 | 启动后识别不完整状态，不误认发布成功或丢失权威正文 |

### 9.2 性能与体验目标

以下均为需要实测的初始目标：正常工作负载下停止输入后约 2 秒内确认本地保存；1 万字中英文混排文章编辑无明显持续卡顿；约 1000 篇测试文章下列表和标题筛选可正常使用；移动端正文、图片与代码块不破坏页面布局。

发布耗时单独记录本地准备、上传、远程构建、部署与线上核验，不把第三方排队时间伪装成本地产品的确定承诺。每次显示“已确认上线”都必须对应证据；这是正确性要求，不是尽可能提高成功率的运营指标。

### 9.3 自用价值评估

首版不用注册数、日活、功能数作为主要成功指标。连续使用后观察：有多少篇真实文章通过完整流程发布；多少次需要绕过 Beacon 手工修复；有没有因流程不清而误发；维护软件是否正在挤占写作时间。

建议先完成 10 篇真实文章的写作与更新，再决定下一个大功能。如果实际工作仍主要发生在外部编辑器，需分析原因，而不是立即增加更多管理面板。

## 10. Vibe coding 实施规范

### 10.1 把本报告作为设计输入，而不是无限授权

代码代理可以负责拆解任务、实现与测试，但不能自行把建议项升级为新需求。尤其不能未经确认就创建或公开真实仓库、上传真实草稿、更改账号权限、植入遥测服务或自动发布文章。

实际开发时先记录最终确定的技术栈、工作区结构和发布策略。M0 只使用明确允许公开的样例内容；真实文章加入前，先完成草稿隔离测试。

### 10.2 每次只交付一个可验证的纵向功能

不要先一次性生成几十个空页面。推荐从“创建文章 → 保存文件 → 重启读回”开始，再做“同一文章 → 本地预览”，最后连接发布和线上验证。

每次交付应说明：修改了什么、用户如何使用、测试如何执行、实际结果、已知限制和恢复方式。不能以“理论上应该通过”替代测试证据；也不能把未实际运行的测试标为通过。

### 10.3 建议维护的文档

项目中保留简洁的产品定义、架构决策、内容格式、发布状态机和验收用例。只有当它们真正需要独立维护时再拆文件，初期不必为凑结构生成大量空文档。

仓库指导文件应明确四条硬规则：不静默覆盖内容；不自动公开草稿；不向前端或仓库写入凭据；不在发布成功缺少证据时显示成功。

AI 写作能力作为后续可选扩展。即使加入，也先采用“建议—审阅—应用”模式；不得默认覆盖正文或自主发布。**Vibe coding 是开发方式，不是 Beacon 的核心价值主张。**

## 11. 主要风险与决策门槛

| 风险 | 后果 | 设计应对 |
|---|---|---|
| 品牌与功能一起无限扩张 | 从个人工具变成难以完成的平台 | 名称承载愿景，MVP 只做一条发布路径 |
| Git 推送被误认为发布成功 | 作者误判读者看到的版本 | 分阶段状态 + 线上版本核验 |
| 最新工作区全部参与构建 | 未确认修改或草稿泄露 | 发布快照 + 白名单导出 |
| 文件与数据库都能改正文 | 数据分叉，故障后无法判定真值 | 明确权威来源，索引单向派生 |
| 本地修改、远程仓库和旧任务冲突 | 内容覆盖或站点倒退 | 版本检查、串行发布、未知状态核对 |
| 原始图片直接进入站点 | 体积过大或不必要信息公开 | 原件/衍生图分离、按需复制 |
| 误把 Git 当完整备份 | 设备故障后数据无法恢复 | 独立备份 + 实际恢复演练 |
| 过早远程化和多平台化 | 凭据、权限、维护复杂度上升 | 单机、单站点验证后再扩展 |
| 为品牌改造所有按钮术语 | 操作难懂，增加误操作 | 品牌可隐喻，操作必须明确 |

进入开发前，需要确定但不必现在购买或创建的事项包括：工作区位置、GitHub 目标仓库与权限、站点地址形式、站点名称、最终技术栈。主 Slogan 和视觉方向也需要一次明确确认；不应在此之前投入精细 Logo 动效和多套主题。

## 12. 建议的产品基线卡

```text
Name
Beacon

Category
Personal Publishing System

Positioning
A personal writing and publishing system for the open web.

Slogan — proposed
Broadcast your ideas.
让思想发出自己的信号。

Primary user
Single author, self-hosted local workspace.

Primary workflow
Write → Save → Preview → Publish → Verify.

Public destination
GitHub Pages.

Content model — proposed
Markdown + portable metadata + managed web assets.

Personality — proposed
Quiet. Focused. Independent. Clear.

Hard boundaries — proposed MVP baseline
One author. One site. One publishing channel.
No silent overwrite. No automatic draft publication.
No false success. No credentials in public output.
```

**最终建议：Beacon 不要先成为一个漂亮的博客后台，而应先成为一个可信的个人发布工具。** 名字提供方向，体验建立信任；信任建立之后，简洁的品牌表达才会有实际内容支撑。

> **Orbit 让素材有来处；Beacon 让思想有去处。**
