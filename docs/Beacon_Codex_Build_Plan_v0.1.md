# Beacon：Codex 构建计划

> 版本：v0.1 · Studio Home 精简版  
> 日期：2026-09-21  
> 交付目标：一个具有 OpenCode 桌面工作台气质、但以写作为中心的 Beacon 作者端。  
> 本轮实施边界：P0 仓库检查 + P1 首页、编辑器与真实本地保存；P2、P3 为后续计划，不自动展开。  
> 核心原则：简化用户面对的功能与界面，不简化内容保存和公开发布的安全底线。

## 1. 给 Codex 的任务说明

你是 Beacon 的资深产品工程师，负责产品交互、前后端实现与验收。请根据本计划先检查项目，再交付一条可运行、可测试的写作流程，不要一次生成完整 CMS。

Beacon 用于个人写作与发布。产品名称为 Beacon，品牌文案使用 `Broadcast your ideas.`。作者后台专注写作和发布，公开网站通过 GitHub Pages 展示。Orbit 管素材，Beacon 管文章；本轮不改 Orbit，也不直接操作其数据库。

本计划中的 Home 指 **Beacon Studio 的作者端首页**，不是读者看到的博客首页。“类似 OpenCode 的桌面”本轮解释为布局与交互参考；没有现成桌面壳时，先做本地 Web 工作台，不自动引入 Tauri、Electron 或原生窗口开发。仓库已有桌面壳时保留，不为执行本计划强行拆除。

产品设计输入来自 `Beacon_Design_Report_v0.1.md`（2026-09-20）。本计划收敛其中的后台导航与首轮开发范围，不撤销“不静默覆盖、不误发、不假报成功”的要求。为避免混淆，本计划独立使用 P0–P3 编号，不沿用旧报告的 M0–M3。

截至编制本计划时，通过当前 GitHub 连接未定位到可审计的 Beacon 仓库。因此下面的技术栈、目录和接口均是**新项目默认方案，不是对已有代码的描述**。不得据此宣称 Beacon 已完成任何功能。

## 2. 先检查，再实施

先读仓库中的 `AGENTS.md`、`README`、已有设计文档、依赖清单、锁文件、启动脚本、测试和数据库迁移。确认当前分支、未提交修改、实际框架，以及现有保存、预览、发布能力。

只检查用户指定或当前明确属于 Beacon 的项目。工作目录不是 Beacon、或无法确认项目位置时，停止写操作，询问项目路径；不要在相邻目录或其他仓库中猜测性初始化。

已有 React / Next.js / FastAPI / 编辑器 / 桌面壳等实现时优先复用。不为了套用新目录而重写已有代码，不顺便升级整个依赖树，不混用包管理器。保留现有可用功能；“收起入口”不等于删除业务能力。已有数据格式与本计划不同，先提出兼容方案，不直接破坏性迁移。

不得执行 `reset --hard`、`clean -fd`、强制推送，或覆盖用户未提交的修改。开发和测试使用临时工作区，不读取、迁移或发布真实草稿。未得到明确授权，不创建远程仓库、不推送代码、不触发真实发布、不更改账号权限。

## 3. 首版产品范围

### 保留

一位作者、一个当前工作区、一个公开站点。主流程为：

```text
打开 Home → 新建 / 继续文章 → 写作 → 保存 → 预览 → 明确确认发布 → 核验线上版本
```

第一轮只做到“打开 Home → 新建 / 继续文章 → 写作 → 保存 → 重启读回”。此时交付的是可用写作原型，不宣称完整发布 MVP 已完成。

### 暂不新增

AI 聊天与自动写作、多模型切换、终端、MCP 管理、多项目树、多窗口编辑、多作者权限、多站点、多平台分发、定时发布、评论、统计仪表盘、插件系统、主题市场和独立素材库。

暂不做自研富文本或块编辑器，不做双链、知识图谱、MDX 和复杂嵌入。没有使用需求之前，不加看板、日历、写作热力图、成就系统或运营通知。

图片在文章内插入，不新增素材管理一级页面。与 Orbit 的连接先采用导入已选文件，不建立运行时依赖。

## 4. 信息架构：两个主要入口，一个轻量设置面板

```text
Beacon Studio
├── 首页 Home              新建文章、最近写作
├── 文章 Articles          搜索标题、筛选、打开文章
├── 编辑器 Editor          由文章进入，不再建一套管理导航
└── 设置 Settings          底部入口，按需打开面板
```

公开网站属于另一个展示界面，不是 Studio 的首页。发布记录在 P3 放入文章的“发布详情”，设置面板提供最近站点发布记录；不单独增加常驻“发布中心”主导航。

### 4.1 应用外壳

左侧仅一条侧栏，右侧一个主工作区。桌面侧栏初始宽度约 216 px，可收起为约 56 px；不要同时摆放图标轨道、项目树、文章列表和编辑器形成三四栏。

侧栏顶部是小型 Beacon 字标；中间为“首页”“文章”；底部为当前本地服务状态和“设置”。默认不展示头像、账户套餐、通知中心、版本推广和帮助卡片。

已有主题时沿用其基础 Token 并减少视觉噪声；全新项目本轮采用单一深灰黑白主题：弱边框、适量留白、清晰文字、少量圆角。只在失败和警告等状态中使用必要的语义强调，不依靠颜色单独表达含义。这里的配色是本轮默认方案，不代表用户已经批准完整品牌规范。

颜色、间距、字号和圆角集中定义为 Token。不做渐变背景、星空、玻璃拟态、大面积光效、持续动画或卡片墙。网页内不伪造可点击的 macOS 关闭、最小化按钮。

### 4.2 Home：只回答“开始什么、继续什么”

主区最大宽度约 760 px，内容放在视觉中心偏上的位置，不做巨大宣传 Banner。

```text
┌────────────────┬───────────────────────────────────────────┐
│ Beacon         │                                           │
│                │                  Beacon                   │
│ 首页           │           Broadcast your ideas.           │
│ 文章           │                                           │
│                │              [ ＋ 新建文章 ]               │
│                │                                           │
│                │ 最近写作                                  │
│                │  为什么写作        草稿         10 分钟前 │
│                │  产品的边界        有未发布修改  昨天      │
│                │  我的第一篇文章    已发布       2 天前    │
│                │                                           │
│ 本地服务状态   │                              查看全部 →   │
│ 设置           │                                           │
└────────────────┴───────────────────────────────────────────┘
```

“新建文章”是首页唯一高强调操作。点击后创建一个真实草稿，获得稳定 ID，再进入编辑器并聚焦标题；创建失败必须原地给出原因，不能跳入不存在的文章。按钮在请求期间禁用，防止连击产生重复空稿。

最近写作最多 6 条，按真实内容修改并保存的时间倒序排列，显示标题、发布关系状态、相对时间。只打开或刷新文章不更新其内容修改时间。行标题为空时显示“未命名文章”，不强制作者先填完标题。点击整行即可继续写作，更多文章进入同一 Articles 列表。

没有文章时只显示“写下第一篇文章。”和新建入口。不填充虚假文章、使用统计或引导任务。加载失败显示错误与重试，不把失败伪装成空列表。

GitHub 未配置时不弹出阻塞式授权界面，不影响新建、保存、离线写作。设置面板可以说明“连接 GitHub 后即可发布”。

普通启动进入 Home；刷新已有文章 URL 时恢复该文章，不强制跳回 Home，也不自动创建新文章。

### 4.3 编辑器：一篇文章占据主区

```text
┌────────────────┬───────────────────────────────────────────┐
│ Beacon         │ 返回    保存状态          预览  发布  ⋯   │
│                ├───────────────────────────────────────────┤
│ 首页           │                                           │
│ 文章           │                文章标题                   │
│                │                                           │
│                │                正文区域                   │
│                │                                           │
│                │                                           │
│ 设置           │                                           │
└────────────────┴───────────────────────────────────────────┘
```

默认只编辑一篇文章，不做标签页管理。标题和正文直接可编辑，正文采用 Markdown，自动换行，默认不显示行号、代码 minimap、终端状态栏或多排工具按钮。

正文初始字号约 18 px、行高约 1.8、最大宽度约 760 px，使用系统中文字体栈。代码片段采用等宽字体。侧栏收起后形成专注写作布局，不再引入独立“专注模式”系统。

顶栏只常驻返回、保存状态、预览、发布和“更多”。P1 尚未实现的预览/发布入口隐藏，或明确禁用并标明未接入；不能点击后弹假成功。已有预览/发布功能不得因阶段划分而被删除。

“更多 → 文章信息”按需打开窄面板，放摘要、slug 等低频字段。草稿允许未填写；发布时才校验必需项。标签、封面等若不存在，不在 P1 新增。

预览默认切换同一主区，退出时恢复光标与滚动位置；不默认展示编辑/预览双栏，也不自动弹出第三列属性面板。

本轮仅新增少量明确快捷操作：在编辑器内用 `Cmd/Ctrl + S` 立即保存，`Esc` 关闭临时面板。不要抢占新窗口等浏览器默认快捷键，不在中文输入法组合输入时执行格式化或快捷命令。

### 4.4 Articles 与设置

Articles 使用普通文章行列表，支持标题搜索、分页和“全部 / 草稿 / 已发布”筛选。“已发布”包含带有未发布修改的文章，并展示相应徽标；P3 的“已撤下”是明确状态，至少可从全部列表找到。

不要把草稿、已发布内容做成互相独立的数据库。不要只为了追求形式加入无限滚动、拖拽排序、分组数据库视图。

P1 不新增删除能力；已有删除能力保留并测试。后续删除本地稿与线上撤下必须分开，不能通过移除本地文件假装内容已经下线。

设置为按需打开的面板。P1 只显示当前工作区位置、本地服务状态和必要说明；P3 再加入站点名称、目标仓库、站点地址与发布连接。不要生成不可用的设置空表单。

## 5. 新项目默认技术方案

已有实现优先于以下默认值。无代码时采用：

| 部分 | 默认选择 | 边界 |
|---|---|---|
| Studio | React + TypeScript + Vite | 本地 Web 工作台，不新增 SSR 服务 |
| 编辑器 | CodeMirror 6 + Markdown 扩展 | 先验证中文输入；不自研富文本内核 |
| Engine | FastAPI | 文件、索引与发布编排集中在一个本地服务 |
| 正文 | Markdown + YAML front matter | 文件是正文与文章元数据的权威来源 |
| 本地状态 | SQLite | 存派生索引及后续发布任务，不另存可独立修改的正文 |
| Site，P3 | Astro 静态构建 | 不维护第二套公开站点生成器 |
| 发布，P3 | Git + GitHub Actions + Pages | 单站点、显式发布、可验证 |

依赖版本在实施时根据已有环境核对、验证并锁定，不凭本计划安装未经核对的最新版。优先复用项目已有组件和测试工具。

GitHub Pages 是静态站点托管，不能承担 Beacon 的 FastAPI 运行与数据库写入；官方说明：`https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages`。

Astro 有官方 GitHub Pages 部署路径，并要求正确处理站点 URL 与项目子路径：`https://docs.astro.build/en/guides/deploy/github/`。P3 只采用其静态构建路径。

beacon/                       # 应用代码

本地服务只监听回环地址。生产式本地启动采用同源 UI/API；开发模式可用 Vite 代理 `/api`。校验 Host、Origin 与本地会话/防伪机制，拒绝未授权写入。不开放通配跨域，不为了单用户而暴露任意文件操作接口。

工作区由明确的启动配置确定；不建设全磁盘文件浏览器，不自动迁移用户目录。文件服务只允许工作区内经过校验的路径，拒绝路径穿越与越界符号链接。

## 6. P1 必须真正做对的保存协议

保存状态与发布状态独立。前端至少区分 `dirty / saving / saved / error / conflict`，界面对应“有未保存修改 / 正在保存 / 已保存到本地 / 保存失败 / 版本冲突”。互联网连接状态也不能与本地服务状态混为一谈。

只在后端确认对应版本完成文件持久化后显示“已保存到本地”。请求已经发送、浏览器缓存成功或 SQLite 索引更新，都不能单独代表正文文件保存完成。

采用约 600 ms 防抖、每篇文章串行保存；在正常本地负载下，停止输入后约 2 秒内完成确认是验收目标，不是已测性能。收到旧请求的成功响应时，只确认该请求携带的内容版本；用户之后的新输入必须继续保持 dirty 并进入下一次保存，不能被旧响应覆盖。

后端使用稳定文章 ID、版本摘要与冲突检查。同目录临时文件写入、必要校验与持久化后原子替换；服务内加锁协调同一文章的写入。另一个标签页或已被观察到的外部文件修改导致版本不匹配时返回明确冲突，不能静默覆盖。

冲突时保留编辑中的文本，提供“保留为副本”或经明确确认后“重新载入磁盘版本”。第一版不需要实现完整差异合并器，但不得因为不做合并就丢掉任一方内容。

离开文章前处理尚未完成的保存；失败时留在当前页面，提供重试与导出当前文本的退路。本地服务断开时可以继续输入，但必须显示未保存，不能假装已经同步。浏览器退出前的提醒只是辅助，不能承诺尚未确认保存的输入一定能恢复。

文件与 SQLite 不当作同一个事务：正文文件为真值，索引失败时标记待修复，启动或下次读取时可重建。返回给客户端的保存结果必须能准确说明文件状态，不通过重新覆盖旧文件“回滚”已经保存的新正文。

### 建议的最小 API 合同

仅在缺少现有接口时建立；已有 API 通过适配复用。

| 接口 | 用途 | 关键约束 |
|---|---|---|
| `GET /api/health` | 本地服务与工作区状态 | 不公开凭据 |
| `GET /api/articles` | 标题搜索、状态筛选、分页、最近排序 | 有稳定排序与分页上限 |
| `POST /api/articles` | 创建草稿 | 新建成功后才导航；支持重复请求保护 |
| `GET /api/articles/{id}` | 读取文章 | 返回正文、元数据和 revision |
| `PUT /api/articles/{id}` | 保存文章 | 带 base_revision；冲突返回 409；成功返回新 revision |

可用 `GET /api/articles?sort=updated_at_desc&limit=6` 支持 Home，不为首页再维护第二份文章集合。

稿件最小字段：`id`、`title`、`slug`、`summary`、`created_at`、`updated_at` 与 Markdown 正文。草稿允许空标题与空 slug。标题与文件身份解耦，修改标题不改文件名。首次发布后锁定 slug；公开发布时间与工作稿修改时间分开。

## 7. 后续 P2：预览与图片，但不做素材平台

补齐 Markdown 的标题、段落、列表、引用、链接、图片、代码块和表格。即时预览与 P3 站点构建使用同一套 Markdown 方言、插件与安全规则，并用共同样例测试；发布前另用 Site 模板生成正式预览，不把编辑区渲染等同于完整站点预览。

预览不执行任意原始 HTML 或 MDX，拒绝危险链接协议。导入图片先完成后端保存，成功后才插入受控相对路径；失败保留用户文本，不插入假地址。不覆盖导入原件；必要的网页衍生图另存。

第一版通过文件选择插入图片即可，粘贴与拖拽可在同阶段按实际成本添加，不以它们阻塞基本写作。支持适当的替代文本与图注。不得把图源链接自动解释为有发布授权。

导出 Markdown 与实际引用附件，并验证在新工作区可读回。关闭 Orbit 后，Beacon 已导入的图片仍可使用。

## 8. 后续 P3：发布入口简单，发布语义完整

P3 的目标是补齐可自用的发布闭环，而不是新增运营后台。GitHub 未连接不影响本地写作；首次连接由用户确认目标仓库、站点地址、访问范围与凭据方式，不能自行猜测并创建公开目标。

用户点击发布后先保存当前稿，生成不可变候选快照并展示标题、目标地址、图片及影响范围。确认后发布同一个候选快照。若正文在确认前变化，候选快照必须失效或重新确认；确认后的继续写作保持私有，不改变已提交的发布任务。

发布快照基于最近已确认站点版本，只替换本次选择的文章。必须通过以下例子：A 已发布 v1，本地改到 v2；只发布 B 时，线上仍是 A v1 + B 确认版，A v2 不得进入提交或构建产物。

每次发布记录 `release_id`、父版本、公开文件清单、内容与图片摘要、模板版本、commit SHA、workflow run ID、阶段、错误和核验时间。内容摘要只覆盖实际公开字段与资源，不因单纯打开文章或私有工作稿时间变化误报新版本。

保存、内容发布关系、任务阶段分别建模。发布关系至少区分草稿、已发布、有未发布修改、已撤下；任务阶段区分准备、推送、构建、部署、线上核验及失败/待确认。

Git 推送成功不能显示“已上线”。仅在对应提交的部署结果与线上公开版本标记吻合后显示“已确认上线”。状态无法读取时显示“待确认”，保留证据供重查，不直接宣称失败或自动重发。

本地用一个持久化任务记录和串行发布执行器即可，不引入 Redis、分布式队列和通用任务平台。存在未核清的旧任务时不得让后续任务越过它盲目发布；线上工作流也要防止旧部署覆盖新版本。重试复用原快照，推送超时先核对远程是否已成功。

更新只更新所选文章。撤下生成不含该文章的新站点，并同步处理首页、RSS 与 sitemap；确认线上版本后才标记已撤下。恢复旧版用新发布记录完成，不默认改写 Git 历史。保留最近发布与恢复入口，但不新增常驻发布仪表盘。

公开网站只建设首页、文章、关于、404，以及 RSS 和 sitemap。正文阅读优先，不把 Studio 的桌面外壳复制到读者站点。集中处理 `site_url` 和 `base_path`，测试项目子路径下的文章、图片和订阅地址。

公开前白名单导出并检查仓库、构建产物、RSS、sitemap、JSON 和附件，确保不包含私有草稿标记、密钥、本地路径和未确认修改。凭据只由后端受控使用，不写前端、正文、日志或导出包。

GitHub Actions/Pages 的构建与部署权限在 P3 对照官方文档实施：`https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages`。不把示例工作流中的动作版本直接当作已验证的项目锁定版本。

## 9. 按阶段交付

| 阶段 | 交付内容 | 完成标准 |
|---|---|---|
| P0：查清现状 | 仓库结构、运行方式、现有能力、最小改动清单 | 指出复用项、缺失项、保护的数据与本轮验收命令 |
| P1：写作 Home | 简洁应用外壳、Home、文章列表、编辑器、真实保存 | 新建 → 输入 → 已保存 → 退出服务 → 重启后完整读回 |
| P2：写作完整性 | 安全预览、文章图片、必要元数据、导入导出 | 内容与资源可预览、可迁移，中文输入和长文体验通过 |

**默认只执行 P0 + P1。** 检查之后可以直接实施本轮最小改动，不要只输出另一份抽象计划。P1 验收结束后交付结果并停止，不自动开始后续阶段。

已有 P2/P3 能力时，P1 可以接入现有功能，但不借机重写其流程。任何需要破坏性数据迁移、真实公开操作或超出本轮的新依赖体系，单独报告并等待确认。

## 10. 验收：用真实结果，不用截图替代保存测试

| 阶段 | 用例 | 通过标准 |
|---|---|---|
| P1 | 首次打开与空状态 | 无 GitHub 配置也能新建；无虚假内容与统计 |
| P1 | 重复点击新建 | 一次用户意图不产生重复文章；失败不进入假编辑器 |
| P1 | 输入、保存、刷新、重启 | 已确认保存的正文与元数据完整；近期文章来自真实数据 |
| P1 | 延迟与乱序响应 | 较旧保存响应不覆盖后续输入、不错误标记新输入已保存 |
| P1 | 服务断开、权限不足、模拟写盘失败 | 显示真实失败；输入保留；能重试或导出；旧文件不被截断 |
| P1 | 两标签页及外部编辑冲突 | 旧 revision 被拒绝，不静默覆盖双方内容 |
| P1 | 路由与滚动 | 文章 URL 刷新可恢复；离开时处理待保存内容；无双重主滚动 |
| P1 | 中文输入、撤销、粘贴 | 不丢字、不重复、不跳光标；组合输入不被快捷键打断 |
| P1 | 基础安全 | 未授权写入、路径穿越和越界符号链接被拒绝 |
| P2 | 图片与导出 | 附件存在、路径可迁移、无假保存与危险脚本执行 |
| P3 | A 私改、只发布 B | A 的私有新版本不进入远程仓库和任何公开产物 |
| P3 | 推送超时、部署失败、重启重试 | 保持正确阶段与证据，不假成功、不夹带新修改 |
| P3 | 更新、撤下与恢复 | 内容及 RSS/sitemap 对应同一已核验 release |
| P3 | 根路径与项目子路径 | 首页、文章、图片、404、RSS/sitemap 路径正确 |

优先用项目现有测试体系；新项目采用后端 pytest、前端组件测试与 Playwright 浏览器测试。浏览器至少覆盖 Chromium 和 WebKit。自动化的 composition 事件测试不能替代真实 macOS 中文输入法手工检查；未实际操作的部分必须列为未验证。

视觉验收提交真实运行截图：1440×900 的 Home、1280×800 的编辑器，以及一个窄窗口。不能用设计稿或生成图片冒充运行截图。验证键盘焦点、面板焦点恢复、文字可读性、长标题省略与长文滚动。

性能目标使用明确数据测量：约 1000 篇样例文章的列表与搜索可用，约 1 万字中英文混排文章输入无持续明显卡顿。记录测试环境和实际结果，不仅写“性能很好”。不得为测试填充用户真实内容目录。

## 11. 本轮交付格式

交付时说明：实际复用了什么、改了哪些文件、如何启动、临时工作区位置、具体测试命令与结果、真实截图、已知限制，以及下一阶段尚未实现的内容。

报告必须区分“已实现并验证 / 已实现但未验证 / 未实现”。类型检查通过不能代替保存、浏览器和真实中文输入测试；模拟发布通过不能冒充真实 Pages 已上线。没有环境执行的项目，直接标注未验证。

不要把建立几十个文件夹、渲染一个静态 Home，或使用 localStorage 保存正文当作 P1 完成。P1 的决定性证据是：**从简洁 Home 开始写一篇真实 Markdown 草稿，并在服务重启后读回已经确认保存的同一份内容。**
